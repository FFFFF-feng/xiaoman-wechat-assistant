# ACP 超时排查与修复

日期：2026-10-16。本机隔离演示已取得真实 Codex 回复；尚未接入生产微信或部署服务器。

## 结论与证据

原问题发生在 Codex 到模型服务的 WebSocket 连接。本机配置的 `custom` provider 声明 `supports_websockets=true`，原生日志出现连接被拒绝（Windows `10061`），随后进入流式请求重试；因此即使 ACP 初始化与建会话成功，也一直没有模型文字。原有45秒和70秒等待并未解决连接失败。

保持现有 ChatGPT 登录和 `gpt-6.1-sol` 模型，通过单次进程配置关闭 WebSocket，改走 HTTP/SSE，原生 `codex exec` 在12.28秒返回预期标记。将相同设置放入 ACP 会话后，两次独立的真实演示均成功；第二次记录完整调用14,602毫秒，同一消息的重复请求复用原结果，没有第二次推理。低推理强度也用于本轮短建议；这些样本不足以量化每项配置对耗时的独立影响。

这证明本机 HTTP 路径可用，不能进一步断言所有网络都不支持 WebSocket。另测的运行时 API 网关虽然可连接，但不识别 `gpt-6.1-sol`（返回400 / `model_not_found`）；该替代路线未采用，也没有改模型或要求重新登录。

| 检查 | 结果 |
| --- | --- |
| 原生 Codex，原 WebSocket 配置 | 连接被拒绝后重试；原45秒探针超时 |
| 原生 Codex，HTTP、低推理、无重试 | 12.28秒，`ACP_NATIVE_HTTP_OK` |
| ACP + Codex，第一次修复验证 | 实际生成中文建议，成功结束；去重复用；未写任务或发送微信 |
| ACP + Codex，第二次修复验证 | 14.602秒，实际生成中文建议；识别今天中午已过，未擅自创建提醒 |
| 另一个 API 网关对照 | HTTP 400 / 模型名称不可用，不是等待更久能解决的问题 |

## 代码改动

`integrations/acp-demo/codex-config.mjs` 只读宿主 `$CODEX_HOME/config.toml`（未设置时为用户 `.codex` 目录），识别当前 provider，对本次 ACP 会话应用：

```toml
# 示意：当前宿主的 provider 是 custom。实际代码按宿主 provider 名称生成覆盖。
model_providers.custom.supports_websockets = false
model_providers.custom.request_max_retries = 0
model_providers.custom.stream_max_retries = 0
model_providers.custom.stream_idle_timeout_ms = 20000
model_reasoning_effort = "low"
```

以上是应用覆盖的键值示意，不应直接粘贴到已有 TOML 表内。代码通过 `CODEX_CONFIG` 传递带点键名的覆盖，保留现有 provider 的地址、认证与请求头；不会将密钥复制进会话配置或修改全局文件。内置 OpenAI provider 使用会话别名，避免重定义保留的 provider 表；该分支有离线检查，本轮真实模型验证使用的是当前 `custom` 配置。

模型流空闲等待上限20秒（较小总预算会相应缩短）；ACP 完整子进程的默认总预算45秒。取消模型内部请求/流的自动重试，外层也不重试 prompt。超时时终止本次子进程树，保留“未成功”的结果，不能把部分输出当成完成。HTTP 演示响应新增 `elapsed_ms` 用于观察完整调用耗时。

解析宿主 TOML 的 `smol-toml` 固定为1.9.1；没有更新全局 Codex/OpenClaw/微信插件。没有改宿主默认模型，也未启用写文件、终端、MCP任务工具或真实微信投递。

## 复现

```powershell
cd integrations/acp-demo
npm ci --ignore-scripts --no-audit --no-fund
npm test
$env:CODEX_PATH = (Get-Command codex.exe).Source
npm run demo:codex
```

需要当前用户已有可用 Codex 登录或其既有认证配置。真实演示会使用现有模型用量，仅提交脚本里的合成文字。成功应返回 `runtime:codex`、非空 `reply`、`elapsed_ms`、`task_write:false` 和 `wechat_send:false`；重复消息返回相同结果。

12项离线检查覆盖既有协议/鉴权/去重/隔离、HTTP配置不改认证或模型、宿主文件不变、非法配置快速失败、超时预算校验，以及实际不响应子进程被外层截止时间终止。

下一步是给生产 Python 的规划类请求增加可关闭的 ACP 路由、持久身份会话、明确的等待反馈和耗时/失败率记录，再做手机灰度验收。当前14秒量级仍需要产品上的等待反馈，不能把本次本地成功视为线上长期稳定性验收。

官方依据：[OpenAI Docs 配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)对 provider 的 `supports_websockets`、请求重试、流重试和空闲超时有单独定义；本机故障判断及修复效果来自上述实际运行记录。
