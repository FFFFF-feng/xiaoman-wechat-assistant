# 小满微信接入：ACP / acpx 验证与隔离 Demo

验证日期：2026-10-16。基线：项目 `cafe36c`，既有宿主 OpenClaw `2026.10.1`、腾讯微信插件 `2.4.10`；演示使用 Node `24.21.0`。本文结论来自公开文档、当前插件源码及本地实际运行，未改变生产微信网关。

## 结论

**可以把 ACP 用作小满调用外部 Agent 的统一接口。它能帮助接入 Codex / Claude Code 的会话与工具执行能力，但不能替代微信消息通道，不能靠换协议解决微信端转发、头像和发送资格。**

隔离 demo 已完成：本地 HTTP 调用真实 acpx，经 stdio 与 ACP v1 Agent 完成初始化、创建会话、发送 prompt、接收分段文字及结束信号；最初6项测试，结合自然表达和超时修复后增至12项。离线 Agent 是固定回答的协议样例，不是模型效果测试。

真实 Codex 最初在原生CLI和ACP两条路径均超时。后续日志定位为WebSocket连接被拒绝后的重试；保持原账号和模型，单次会话改用HTTP后，原生CLI及两次ACP真实调用成功，第二次ACP调用14.602秒。详见[超时排查与修复](ACP超时排查与修复_2026-10-16.md)。生产微信仍未接通ACP；Claude本轮未安装、登录或实测。

## 老板说的协议具体是什么

这里的 ACP 是 **Agent Client Protocol**。它定义客户端与 Agent 间的双向通信；目前稳定文档为 v1，v2 标注为 Draft。典型流程是 `initialize → session/new → session/prompt`，Agent 通过 `session/update` 流式报告文字、工具状态和计划，支持取消与权限交互。[ACP 初始化](https://agentclientprotocol.com/protocol/v1/initialization)、[Prompt Turn](https://agentclientprotocol.com/protocol/v1/prompt-turn)

这几项需要区分：

| 名称 | 作用 |
| --- | --- |
| ACP | Client 与 Agent 的协议，不是微信接口，也不是一个大模型 |
| `acpx` | 无交互界面的 ACP 命令行客户端，可从脚本调用多个 Agent |
| `@openclaw/acpx` | OpenClaw 的 ACP 运行后端插件，把外部 Agent 接到宿主 |
| `@agentclientprotocol/codex-acp` | 将 ACP 请求转换成 Codex App Server 操作的适配器 |
| `openclaw acp` | 反方向：把 OpenClaw 暴露给 ACP 客户端；不等于启动外部 Codex/Claude |
| MCP | 给 Agent 暴露工具/数据的协议；后续可用来提供受控的小满任务工具，与 ACP 分工不同 |

新安装应使用 `@agentclientprotocol/codex-acp`，原 `@zed-industries/codex-acp` 仓库已注明迁移。Codex 的原生可集成接口是 App Server，ACP 适配器建立在其上，而不是把 `codex exec` 文本输出包装一下就叫 ACP。[Codex 适配器 README](https://github.com/agentclientprotocol/codex-acp)、[旧仓库迁移说明](https://github.com/zed-industries/codex-acp)、[OpenAI Docs：App Server](https://developers.openai.com/codex/app-server)

## 对当前小满能解决什么

| 问题 | ACP 的帮助 | 仍要做的工作 |
| --- | --- | --- |
| 接入 Codex、Claude Code 等 Agent | 可以统一请求、会话、更新、取消与权限处理 | 安装适配器、准备各自认证及模型路由，并实测实际账号可用性 |
| 复杂任务拆解、给出 A/B/C 建议 | 可以调用已有 Agent 执行框架，更方便扩展规划流程 | 仍需小满的人设、默认时间策略、输出约束和效果测试；协议本身不提升模型智力 |
| 多轮上下文 | ACP 有会话能力，acpx 有持久会话管理 | 按可信账号及发送者映射会话、做并发和过期控制；本 demo 只用一次性会话 |
| 创建、修改和取消小满任务 | 以后可以给 Agent 受控工具 | 现有业务未自动暴露；需要按 owner 隔离、校验时间和幂等，不能让 Agent 直接访问全部数据库 |
| 图片、文件与聊天资料 | ACP 有内容及能力协商，适配器能力也各不同 | 微信先把附件提供出来，之后再做内容校验和格式转换，不能省略入站校验 |
| 微信原生逐条/合并转发 | **不能靠 ACP 解决** | 联系人必须能被微信客户端选择，插件还须收到正文；当前入口限制仍在 |
| 自动修改微信联系人头像/昵称 | **不能靠 ACP 解决** | 取决于微信侧提供的接口或用户手动设置 |
| 隔夜、长期主动提醒 | **不保证** | 微信发送上下文、授权和限流仍由平台决定；原有投递队列也不能省略 |

acpx 官方文档提供 `exec` 一次性调用、命名持久会话、JSON 输出、超时、取消和权限策略。OpenClaw 明确区分 ACP 外部 Agent 与默认原生 Codex 路线；工具桥接也不是默认自动开放。[acpx CLI](https://github.com/openclaw/acpx/blob/main/docs/CLI.md)、[OpenClaw ACP quickstart](https://docs.openclaw.ai/tools/acp-agents/quickstart)

## 当前项目为什么不能只安装插件就切过去

目前的实际链路：

```text
微信私聊 → 腾讯微信插件 → 小满 before_dispatch 接管
                                      ↓
                     Python 鉴权/绑定/去重 → 百炼模型与任务逻辑
```

`integrations/openclaw-xiaoman/index.js` 返回 `handled:true`；连续文字还经过自己的持久合并队列。仅安装 `@openclaw/acpx` 不会让这条已被接管的业务链路自动改用 ACP。

建议未来由 Python 或单独的内部服务明确调用 ACP，让微信插件继续负责收发，Python继续负责身份、任务校验和最终落库。先以独立开关用于只读的聊天/规划，成功后再评估限定范围的任务工具。不要同时开启两套自动回复，造成重复回复、重复模型调用或重复任务。

OpenClaw 的会话绑定还依赖渠道适配能力。当前源码只声明微信私聊能力，不能从 Discord/Telegram 的 `/acp spawn --bind here` 示例推断微信端已支持相同绑定；本轮没有在真实微信会话里执行该命令。[OpenClaw ACP bindings](https://docs.openclaw.ai/tools/acp-agents/bindings)

## Demo 如何复现

目录：[integrations/acp-demo](../integrations/acp-demo/README.md)。独立 `package.json`、lockfile，不改变生产依赖。

```powershell
cd integrations/acp-demo
npm ci --ignore-scripts --no-audit --no-fund
npm test
npm run demo

# 已有 Codex 认证时，可显式尝试真实 Agent；会消耗其现有用量。
$env:CODEX_PATH = (Get-Command codex.exe).Source
npm run demo:codex
```

本地服务仅绑定 `127.0.0.1`，随机端口、内存 Bearer token，只接受固定合成身份。演示脚本发出请求、核对重复请求结果，随后关闭服务。

真实 Codex 运行模式采用只读预设，acpx 不提供客户端文件/终端能力，并拒绝工具权限；这不是对外部原生进程的 OS 沙箱保证。没有挂载小满任务工具，不加载微信凭据或项目 `.env`。Codex 继续使用宿主原有认证/网关路由；它自己的合成会话存储仍受其原生规则管理。

## 本轮实际证据

| 检查 | 结果 |
| --- | --- |
| acpx `0.19.5` + ACP SDK `1.8.0` | 真实 stdio 协议握手、会话和文字分段返回成功 |
| 离线 HTTP demo | 成功返回“建议12:00，备选12:30或18:00”的固定样例；同一请求复用结果 |
| 当前12项测试 | 含鉴权、绑定、额外字段、长度、隔离、去重冲突、并发、超时错误、失败不重试、表达规则/参考时钟、配置隔离及真实子进程超时清理 |
| 权限探针 | ACP Agent 请求执行权限，被 acpx 拒绝；按非成功状态结束，不冒充完成 |
| 用户可见输出 | 仅返回成功结束的 assistant 文字；思考、原始工具和供应商错误不回传 |
| Codex ACP adapter `2.2.2` + 已安装 Codex CLI | 原配置45秒/70秒超时；HTTP会话覆盖后连续两次取得真实建议，第二次完整调用14.602秒 |
| 原生 Codex CLI 对照 | 原WebSocket连接被拒绝后超时；保留原账号/模型改用HTTP、低推理及无重试，12.28秒成功 |
| Claude Code | 未实测；不能因为文档有适配器就记为成功 |
| 实际微信消息与任务 | 没有接入真实消息、没有创建任务、没有发送微信，未修改服务器配置 |

诊断记录只保存在被 Git 忽略的本地缓存，供应商原始事件不写入公开文档。这个 demo 的去重只在内存，重启失效；它验证协议与调用边界，不替代生产的持久会话、撤销、配额、监控或微信端验收。
