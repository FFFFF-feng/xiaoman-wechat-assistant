日期：2026-10-16。目标是让用户少填信息、方便改口，同时清楚知道哪些事情已经执行。微信继续负责收发，Python 负责身份、任务与投递，ACP 为复杂建议提供可替换的 Agent 接口。

2026-10-16 部署更新：自然表达、默认中午时间、自然改期及亮色日程页已上线，服务器Python219项、连接器69项离线回归通过；ACP仍仅为隔离演示，未进入生产微信。具体部署范围、保留数据和验收边界见[上线记录](日程与自然表达部署验收_2026-10-16.md)。

## 后续按这个顺序推进

| 顺序 | 工作 | 验收标准 | 前置条件 |
| --- | --- | --- | --- |
| 1. 先验收本轮交互 | 小范围发布；手机验证中午默认、连续改期、否定、跨用户、图片和通知语气 | 同一提醒改期不增加数量；时间和事项完整；真正收到一条回复；提醒投递结果可追踪 | 完成本地检查，部署并由手机验证 |
| 2. 接通 ACP 真实只读建议 | 本地真实推理和超时修复已完成；下一步给规划类请求加独立开关、持久会话、等待反馈与耗时统计 | 合成请求连续返回有效建议；隔离会话；超时有简短反馈；零任务写入、零双重回复；记录耗时与失败率 | 原生和ACP真实回复已通过；仍需生产接入及手机灰度验收 |
| 3. 完成建议交互 | 用户发“事情好多”“周报怎么开始”时给一个可执行起点；确有需要再给两三个选项 | 不编造用户进度；不连续追问；建议与提醒分开；用户改口后规划一致 | 第二步可用后再灰度 ACP；现有模型也可先用于效果对照 |
| 4. 资料转任务草稿 | 图片、文件、聊天记录提取有来源的事项，呈现事项/时间/负责人缺口，供用户选择 | 后文撤销优先；模糊日期保留原文；没有选择时不落库；选中后仍校验时间及归属 | 收集本轮手机资料样本并确认入口能收到正文 |
| 5. 向 Agent 暴露受控任务工具 | 优先只读待办查询，再提供草稿提交、指定任务改期等小范围操作 | owner由服务器注入；schema、幂等键、版本/状态检查及审计；越权和重复请求无副作用；只用真实成功结果生成回执 | 第二步稳定，第四步草稿协议明确；不可把数据库、SSH或通用终端直接交给Agent |
| 6. 用户选择的跟进 | 用户明确开启后支持轻量跟进、完成归档与停止跟进 | 可随时关闭；频率有限；不重复投递；被拒绝/未知发送结果不自动重发 | 微信投递窗口、授权与隔夜提醒实测；后端持久状态可恢复 |

每步完成相应代码、离线检查、合成模型检查和必要手机验收，再推进下一步。ACP的本机真实推理阻塞已解除，第二步仍需完成生产路由和手机验收，详见[超时修复](ACP超时排查与修复_2026-10-16.md)。

## 结合老板建议后的产品选择

“中午先按12点安排”是已实现的明确默认值，用户可一句话改期。没有依据的时间不继续扩大默认范围；“晚点”仍需确认。建议类对话可以先给可行起点，涉及真实提醒的日期、对象和授权则继续校验。

竞品应通过同一组输入对照：生活照、通知截图、长文档、后文撤回的聊天记录、模糊时间、自然改口和多用户。比较回复是否自然、事实是否完整、操作是否正确、等待是否可接受、失败是否说清；不以卖萌程度或文字更短作为唯一目标。此前读取小红书公开页面不等于实际使用过对方机器人。

ACP 解决外部 Agent 的调用接口，不能让微信新增可转发联系人，也不能让没有正文的原生合并转发卡片自动变成可读记录。现有微信入口限制继续按 [ACP验证](ACP接入验证_2026-10-16.md) 和 [资料说明](MATERIALS.md) 处理。
